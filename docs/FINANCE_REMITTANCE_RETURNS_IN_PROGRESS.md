# Actual remittance returns

v0.7.93 development checkpoint from v0.7.92 (`afadb21`) on `codex/finance-remittance-returns`; this does not establish every remitted-tax correction or production acceptance.

## Implemented checkpoint

Treasury records actual receipts into the original bank account with explicit original-liability shares, date, bank/recipient reference, reason and filing disposition basis. `RemittanceReturn` retains immutable proposals, independent Accounting decisions and the versioned posting request. Partial/multiple receipts cannot exceed original posted debit allocations. Stale submissions, invalid dates/amounts, duplicate shares, over-return, self-review, foreign-office and UAT mutation are rejected. The original completed batch and outgoing journal remain unchanged; its editable `returned` status is never reused for a cash refund.

Approval pins the source, filing versions/checksums and allocations. The incoming journal credits selected original liabilities and debits the original bank, retaining original cash-flow purpose with the incoming sign and explicit source-line lineage. Partial receipts do not masquerade as complete journal reversals. Generated lines remain immutable. Detached reversals of incoming journals or original payments with active incoming journals are rejected. The original batch lock serializes decisions and the original Finance journal is locked at materialization. Posted Finance receipts remain held from withholding availability until default-store reconciliation completes. Interrupted handoffs recover the same journal; discarded drafts get exact-payload successors retaining approval, with numbering based on the JEV year.

Ordinary web entry, independent review and a role-scoped review queue are connected. The original CSV retains the outgoing JEV. A separate return CSV identifies original/incoming JEVs, allocated/posted receipts, bank evidence and filing disposition. Filing mutations use batch-first locking. A cash receipt does not amend or erase verified filing evidence; its original bytes remain exportable and the separate independently reviewed amendment path remains available.

## Verified current contracts

- `vouchers/remittances.py` records an actual outward release in an immutable `RemittancePostingRequest`, independently posts it and advances the batch to `completed`. It has no incoming refund/return action. A discarded draft can acquire a successor request, but a posted remittance cannot be replaced.
- `TreasuryRemittanceBatch.save()` protects the original schedule, fund, bank, payment date, recipient and rule after approval. Its current `returned` status means a draft returned for correction and permits schedule edits; it must never be reused to mean money returned after payment.
- `RemittancePostingRequest` already provides versioned immutable evidence and cross-store materialization/reconciliation identities. `RemittanceEvent` is append-only. These can retain an independently reviewed return without replacing the original payment or introducing a generic workflow framework.
- `accounting.services.create_reversal()` can currently prepare a detached remittance reversal. v0.7.92 preserves its transaction classification and correct dated capacity, but this does not reconcile the operational batch or prove bank/recipient receipt. An incoming workflow must connect the actual evidence to its own posting request and preserve exact financial lineage.
- `vouchers/tax_filings.py` permits filing preparation only for released/posting or completed batches. Amendments explicitly version existing evidence. A refunded status alone would strand legitimate amendment work unless this contract is updated. Existing verified filings must remain historical evidence; cash receipt cannot silently erase or amend them.
- `vouchers/remittance_register.py` has separate preparation, independent review and release queues. New return actions need equivalent role/office-scoped visibility. Current outward release permissions and UAT denial must remain enforced.
- `export_batch_csv()` currently prints the latest posting request beside every original allocation row. Once return requests exist, this would incorrectly present an incoming return JEV as the original outgoing payment. Preserve the original payment columns and expose return allocations/JEVs separately in the retained output.
- Filing submission/review/amendment currently locks filing evidence first; draft save locks the batch first. Return review that pins filing decisions must establish a consistent batch-first lock order across those mutations before relying on the captured filing state.

## Required implementation and proof

Retain original outward payment evidence. Treasury records the actual return date, bank/recipient receipt reference, amount and reason. Accounting independently reviews the source, return evidence and filing implications. An approved return creates its own immutable source request and independently posted incoming journal. Reconciliation records the operational result once and supports interruption between stores. The ordinary web detail/register, available withholding, claim correction and retained export must agree.

Keep the original completed batch as the historical outward payment. Derive returned/remaining amounts from its separately retained posted return requests rather than reusing the editable `returned` state. This also avoids making a partial return overwrite the original total or release details. A dedicated return record or request/event representation must support multiple explicit partial returns; choose the simplest representation that preserves independent decisions, allocation capacity and recovery.

For a complete return, preserve an exact reversal of the original financial lines. Partial returns require explicit original-liability allocations and remaining-return capacity, rather than an invented proportional allocation or a full reversal. A credited amount reduced by fees is not a complete return. Neither scenario may rewrite the original batch or pretend the recipient returned money merely because a journal was reversed.

Tax-filing handling must distinguish retained historical filing from an independently verified amendment or other documented agency disposition. A cash return must not automatically mark a filing corrected. Keep filing review actionable on the returned batch and retain any successor evidence. A full-return-only implementation would be an intermediate milestone, not completion of remitted-withholding correction.
