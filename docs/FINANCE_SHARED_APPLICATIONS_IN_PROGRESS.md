## Concrete missing behavior

One original historical payment can settle invoices represented by several original credit lines. The pre-checkpoint single-credit attribution service assigns each selected application wholly to one credit and rejects a second attribution using that line. The v0.7.87 invoice splitter likewise requires each selected application to reconcile completely within its one source credit. Those guards correctly prevent double use; removing them would overstate applied amounts or lose original-line reversal meaning.

For example, a posted 500 payment allocated 300 to one 1,000 credit and 200 to another 800 credit must leave 700 and 600 outstanding, totalling the ledger's 1,300. An exact return must restore the same 300/200 shares. Allocating 299/201 on return is invalid even if a later payment leaves both credits with sufficient balances.

## Current calculation boundary

`accounting/shared_claim_allocations.py::normalize_shared_allocations` accepts the real credits, historical applications and explicit invoices grouped by source ID. Every source is selected once, each original credit reconciles to its invoices, and every application reconciles across the complete group. A source may contain one invoice or several. Invoice identities remain unique across the group; office, fund and liability account must match. Amounts remain exact centavos.

The existing invoice calculation is reused over temporary amount projections of the original application objects. Those copies retain real source identities solely for calculation; no fabricated journal ID, source rewrite, approval, reservation or posting occurs. Per-credit and per-invoice chronology/capacity and exact reversal shares remain mandatory. Later returns cannot fund earlier shortfalls. The public single-credit calculation retains its two-invoice and full-application requirements.

## Proposal persistence implemented locally

Migration `accounting/0025_shared_claim_proposals.py` adds immutable `SharedPayableClaimProposal` records. The service in `accounting/shared_claim_proposals.py` locks the existing fund, then selected source/application lines in ID order. It validates real posted unlinked sources, governed payees, complete allocations, outside-cohort ownership and the versions of current approvals. It seals normalized rows, the complete original source snapshots, source-set identity, actor and explanation. Ordinary database uniqueness protects fund/source-set/version; two submissions based on the same latest version must not create competing first versions.

Each saved proposal is a new retained version. Normal save/delete cannot rewrite it; verification detects changed retained evidence. Proposal creation leaves approved heads untouched. A saved proposal does not authorize spending; the independent review service below must approve it under current source/ownership/capacity checks.

## Independent group decisions implemented locally

`shared_claim_proposals.review` rereads the sealed proposal under fund, sorted source/application and proposal locks. A different currently authorized reviewer records one common decision. Returns retain all member records without moving heads and cannot be replaced by a second decision. Approval requires the latest proposal version and exact current base approvals, rechecks original evidence and normalized allocations, retains every member of any existing shared group, and excludes outside ownership. It freezes allocations used by native applications or reservations.

The service creates all immutable per-credit members, sets one decision timestamp after member creation, then moves every head within the same transaction. It validates complete retained/current groups, invoice identities using database collation and each credit/invoice's capacity before commit. Failure rolls back members and heads together. Compatible documentary successors retain original invoice allocations and pinned earlier reversal/reservation approvals. A coordinated successor recognizes an existing complete native shared reversal rather than demanding its adoption as a second historical application.

The current projection/reversal tests now call this actual proposal and independent review service. Earlier reader/reversal validation used constructed decisions; that historical evidence remains labelled below. The subsequent web/DV validation section below now covers ordinary HTTP entry/review and concrete shared settlement/correction scenarios.

### Exact native shared reversals implemented locally

`accounting/shared_claim_applications.py` retains all original credits and their pinned invoice shares in the existing `JournalLine.payable_allocation` JSON field. A shared reversal has no misleading single `payable_origin`; its `sources` map carries every participating credit. The original journal is still mirrored line-for-line. No second ledger, replacement financial rows or retrospective edits are introduced. Historical approval members retain protected relational references to the source credits.

The existing reversal service captures the complete envelope. Submission and independent posting validate same office/fund/account, exact date/amount/responsibility center, complete approved decisions, original source/invoice shares and whole-journal reversal. Native reversals retain their complete predecessor envelope; compatible later historical approval versions cannot replace the pinned original decision. The posting audit seals the whole envelope and financial amount. Multi-source evidence cannot be used for an unrelated new payment or a reserved single-claim override.

Native application queries use a common single-FK-or-JSON-source lookup, supported by SQLite and MySQL. Parent capacity uses per-credit amount projections; invoice capacity, claim CSV and subsidiary projections retain the same shares. Posting locks all affected original credits in sorted order and revalidates after locking. A reversal of the return reapplies the original shares and competes for the same capacity as an ordinary invoice payment. The current tests use independently approved shared proposals before actual native reversal/posting and report services; the earlier reversal-only phase used prepared decision fixtures.

The ordinary page in `shared_claim_views.py` selects actual credits and earlier applications, then allocates invoice rows by credit. Refresh/add actions retain unfinished input without submission errors; actual submission still requires documentary evidence and completeness confirmation. A shared member's old single-credit page redirects to the complete group. Current approvals and retained decisions are visibly distinct; only the latest undecided proposal offers approval. UAT viewers cannot prepare or review, even with operational permissions; other departments cannot read these sources.

`vouchers/test_shared_historical_payables.py` starts from that HTTP proposal and separate-account review, then uses actual DV validation, governed posting requests, Treasury instruments/advice/release and correction services. It demonstrates invoice selection across two original credits, exact per-claim deductions, full payment/reissue, partial-check closing return, interrupted handoff/closing recovery and immutable archived claim CSV. Earlier historical sources are unchanged and payment does not recognize expense again. These are concrete synthetic office scenarios, not local operator acceptance or proof of exact statutory print layouts.
