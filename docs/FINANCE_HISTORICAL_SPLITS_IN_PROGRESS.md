# Historical invoice allocations — v0.7.87 checkpoint

Implemented on `codex/finance-historical-claim-splits`, from verified v0.7.86 (`38a1b79`). The checkpoint covers reviewed invoice rows within one original credit, native applications/reversals, invoice DV settlement and ordinary proposal entry. Automated HTTP scenarios connect proposal and independent approval to settlement, correction and CSV output; synthetic browser checks cover entry/approval and field readability. Earlier phase notes below retain their historical local/uncommitted/pause status. Shared applications across distinct original credits, generated-history adoption, later corrections and real operator acceptance remain unfinished. ## Implemented calculation boundary

`accounting/claim_splits.py::normalize_allocations` accepts the original credit, its selected historical application lines and explicit invoice rows. It produces canonical exact-centavo allocations without writing any record. Recognized invoice amounts must total the original credit, every selected application must be allocated in full, and no invoice may exceed its own capacity at an earlier date. A later restoring credit cannot cure an earlier shortfall. Every reversal retains the shares of its original line, including reversal of the original recognition. Balanced reassignment between invoices is rejected.

Rows carry stable UUID identities, payee keys, invoice references, recognized amounts and application shares. This is a calculation contract only. Its caller must still establish permissions, posted status, office/fund/account/payee scope, complete exact journal reversal lineage, current approval versions and locks. Case-folded duplicate detection here does not replace native collation-aware identity enforcement.

## Reviewed persistence and read-side integration

Migration `accounting/0022_historical_claim_slices.py` adds `PayableClaimSlice` rows within each attribution version and a sealed allocation checksum on the attribution. Each invoice stores its stable key, payee, reference, recognized amount and historical shares. Ordinary unique constraints cover version/key and version/payee/reference; approval and native claim recognition also share the existing fund lock and native collation-aware checks against currently approved slices. Previous whole-claim approval payloads retain their original shape.

`claim_attributions.propose(..., allocations=rows)` reuses the posted-source, historical application, governed-payee and actor checks. It seals canonical invoice rows before independent review. Review rechecks the rows, digest, sources, current version, duplicates and retained whole-claim reservations. Model saves cannot edit retained invoice rows. Approval verification captures the selected rows for consistent subsequent report projection, while an explicit new verification rereads the retained rows.

The existing review page displays each proposed invoice and its payment/reversal shares. Claim screen/CSV recognized amounts use each invoice's share. Payable subsidiary projection emits separate invoice details over real original journal IDs; report evidence retains each slice key and approval digest. Source-line counts count distinct original journal lines, with a separate allocation-row count where needed. No journal or stored subsidiary detail is rewritten.

## Native applications and reversals

Migration `accounting/0023_journal_invoice_allocation.py` adds `JournalLine.payable_allocation`: the original approved attribution evidence plus exact invoice shares. `bind_allocation` captures that evidence for a draft, and the ordinary journal-line form now offers a scoped invoice selector. Posting checks the original credit and every invoice's dated capacity under the source lock. A later return cannot cover an earlier invoice shortfall.

Historical and native payment reversals preserve the original financial line count, sequence, account, amount and invoice shares. Native reversals also retain the original application's approval version. The temporary split-reversal refusal has been removed. The original credit can be reversed only when its applications have been restored sufficiently on the relevant dates. Current claim/subsidiary projections include these new lines and retain their pinned allocation evidence.

The independently posted audit event retains each invoice line's source, amounts and allocation. Reads and reversals verify native posted shares against that event as well as their original approval. This supplements the existing immutable journal and generated-line edit guards. Existing whole-claim posting event payloads and historical source checksums remain unchanged when no invoice allocation exists.

## Invoice DV integration

Migration `accounting/0024_invoice_reservation.py` adds an immutable nullable invoice key to each Finance reservation. An invoice hold retains the original journal identity/credit, its own recognized amount and the approved attribution version. Whole-claim snapshots retain their earlier shape. Capacity checks enforce both the original credit and the selected invoice, including dated recovery and future movements. Native invoice applications now account for outstanding DV holds as well as posted payments.

The existing consolidated-DV allocation table accepts whole claims and individual invoices from the case's payee/fund. A single invoice can also use this table. Members are identified and ordered by original credit plus invoice key, so two invoices under one credit remain distinct throughout immutable group evidence and check allocations. Deterministic invoice-member keys fit the reservation field without depending on source/version string length. The existing default-case/Finance-source lock boundary and all-or-nothing group transaction are retained.

Generated deduction, payment, cancellation/return and correction lines retain the invoice reservation and exact approved shares. Returned payment matching checks the original allocation alongside the original sequence/account/amount/reservation. Closing a partial check retires only its independently posted shares on the actual return date. Earlier retries cannot spend later restored capacity. The temporary split-DV validation refusal has been removed.

The attribution page now offers an invoice table for consolidated historical credits. Preparers select earlier applications, refresh their share columns, add/delete invoice rows and submit exact amounts through the existing governed service. Refresh/add actions do not create proposals. Invalid totals and incomplete application shares retain entered values for correction. A returned proposal seeds a new version with the same invoice identities; retained proposals remain unchanged. Independent review continues on the existing page.
